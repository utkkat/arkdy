# Выбранные библиотеки

Выбор для текущего Go-прототипа arkdy, 2026-11-02. Приоритеты: простой API,
небольшое число разных технологий, удобная сборка и разумные затраты CPU/памяти.
Это инженерный выбор по документации библиотек, а не результат бенчмарка arkdy.
Границы компонентов сохраняются по [архитектуре](architecture.md).

| Компонент | Выбор | Причина |
| --- | --- | --- |
| Клиентская БД | `database/sql` + [`modernc.org/sqlite`](https://pkg.go.dev/modernc.org/sqlite) | SQLite без CGO и отдельного сервера; обычные SQL-запросы, индексы и транзакции. |
| Хранилище mailbox | Тот же драйвер SQLite, отдельная база узла | Один движок для изучения и сопровождения. Очереди, prekey bundles и сроки хранения выражаются таблицами и индексами. |
| Ratchet, IK и prekeys | [`go.mau.fi/libsignal`](https://pkg.go.dev/go.mau.fi/libsignal) | Готовые операции с ключами и сессиями и заменяемые хранилища; меньше собственного криптографического кода. Выбран для прототипа, лицензия GPL-3.0. |
| HPKE для локальной истории | [`crypto/hpke`](https://pkg.go.dev/crypto/hpke) | Реализация RFC 9180 в стандартной библиотеке начиная с Go 1.26. |
| Password KDF | [`golang.org/x/crypto/argon2`](https://pkg.go.dev/golang.org/x/crypto/argon2), `IDKey` | Argon2id; память и время настраиваются под устройство. |
| Симметрическое wrapping | [`golang.org/x/crypto/chacha20poly1305`](https://pkg.go.dev/golang.org/x/crypto/chacha20poly1305), `NewX` | XChaCha20-Poly1305, единый Go API и длинный nonce для случайной генерации. |
| Сетевой транспорт | Уже используемый [`go-libp2p`](https://pkg.go.dev/github.com/libp2p/go-libp2p) | Сохраняет существующую модель узлов, прямых соединений и circuit relay. |
| Границы сетевых сообщений | [`github.com/libp2p/go-msgio`](https://pkg.go.dev/github.com/libp2p/go-msgio) | Varint-префикс длины и ограничение размера при чтении; модуль уже есть в зависимостях. |
| Кодировка конвертов и RPC mailbox | [`google.golang.org/protobuf/proto`](https://pkg.go.dev/google.golang.org/protobuf/proto) | Бинарный формат, типизированный Go-код из `.proto`; модуль уже есть в зависимостях. |
| Push gateway, FCM | [`firebase.google.com/go/v4/messaging`](https://pkg.go.dev/firebase.google.com/go/v4/messaging) | Официальный SDK; авторизация и API провайдера не реализуются вручную. |
| Push gateway, APNs | [`github.com/sideshow/apns2`](https://github.com/sideshow/apns2) | Небольшой Go API для HTTP/2 APNs и token authentication. |
| SDK блокчейн-адаптера | [`github.com/ethereum/go-ethereum/ethclient`](https://pkg.go.dev/github.com/ethereum/go-ethereum/ethclient) | Типизированный клиент для EVM RPC; выбран для EVM-адаптера, не означает выбор конкретной сети. |
| Защита ключей на телефоне | [Android Keystore](https://developer.android.com/privacy-and-security/keystore) / [iOS Keychain](https://developer.apple.com/documentation/security/keychain-services) | Нативные адаптеры `vault`, которые сохраняют предусмотренную архитектурой привязку к устройству. |

## Хранение

Вместо отдельного bbolt для mailbox выбран тот же SQLite. Клиентская база и база
mailbox имеют разные файлы, схемы и владельцев; выбор одного драйвера не объединяет
архитектурные компоненты. Mailbox хранит ciphertext и публичные bundles, клиентская
БД - sealed/wrapped данные, контакты и outbox.

Начальная конфигурация для файловых баз: WAL, короткие транзакции, ограниченный пул
соединений и индексы по очереди/порядку сообщения и сроку хранения. TTL обслуживается
периодической очисткой. Изменение состояния ratchet и запись соответствующего
outbox-сообщения нужно согласовать одной клиентской транзакцией.

Выбор modernc упрощает сборку на текущей Windows-машине и поддерживаемых настольных
и серверных платформах. Документация драйвера отмечает проигрыш нативному C SQLite
на CPU-нагруженных запросах; абсолютного преимущества по скорости здесь нет.
Android/iOS отсутствуют в опубликованном списке поддерживаемых платформ modernc:
этот выбор ещё не подтверждает мобильную сборку. При переносе нужно проверить драйвер
на целевой платформе, сохраняя SQL-контракт `db`.

## Криптография

`go.mau.fi/libsignal` используется как движок внутри `ratchet`. Для IK и prekeys
выбраны `util/keyhelper`, для подписи и проверки identity-записей - `ecc`, для
сеансов - `session`, для внутренней сериализации - `serialize.NewProtoBufSerializer`.
Интерфейсы `state/store` реализуются адаптером через `vault` и `db`: библиотечные
records не сохраняются в открытом виде. Это сторонняя реализация, а не официальный
Go SDK Signal; выбор для прототипа не является подтверждением безопасности выпуска.

Формат libsignal не заменяет внешний конверт из схемы. В частности,
[`PreKeySignalMessage`](https://pkg.go.dev/go.mau.fi/libsignal/protocol#PreKeySignalMessageStructure)
содержит IK отправителя, а ratchet-сообщения содержат заголовок. Их нельзя просто
поместить в открытые поля mailbox-конверта. Способ защиты этих полей ещё требуется
реализовать в адаптере; пока требование скрытого отправителя не выполнено.
Алгоритмы шифрования сетевых сообщений остаются согласованными с выбранным движком.

Для HPKE `vault` выбран профиль DHKEM(X25519, HKDF-SHA256), HKDF-SHA256,
ChaCha20-Poly1305. Storage key генерируется отдельно от IK и libp2p-ключа.
Для привязки `chat_id` и `msg_id` через AAD нужны `hpke.NewSender` / `NewRecipient`
и методы `Sender.Seal` / `Recipient.Open`: короткие функции `hpke.Seal` / `Open`
не принимают AAD. На каждый независимый sealed record создаётся новый контекст.

Для симметрического wrapping выбран XChaCha20-Poly1305, для password KDF - Argon2id.
Параметры KDF сохраняются с salt и подбираются по времени на целевом устройстве;
ускорение ценой слабого password KDF не является целью. Нативная защита аппаратным
ключом остаётся отдельной частью `vault`; один Argon2id её не заменяет.

## Сеть, push и blockchain

Конверты и RPC mailbox описываются Protobuf и передаются по libp2p с framing от
go-msgio. Получатель задаёт максимальный размер кадра до выделения памяти под него.
Существующие send-функции пока пишут сырые байты: выбор формата ещё не меняет их
поведение и требует согласованной реализации обеих сторон.

FCM/APNs SDK предназначены для серверной части gateway. При реализации клиентской
регистрации и gateway их следует держать в разных пакетах, чтобы серверные SDK и
учётные данные провайдеров не попадали в мобильный клиент. Push передаёт уведомление
о доступных данных, а не текст сообщения. `push_blob` должен оставаться непрозрачным
для mailbox; его формат и ключи gateway ещё требуют реализации.

Выбор `ethclient` относится только к SDK EVM-адаптера. Сеть, контракт, стоимость
операций и способ on-chain проверки подписи текущего IK пока не определены.
Подпись транзакции Ethereum-кошельком не заменяет разрешение на обновление от IK.
Если это требование нельзя реализовать приемлемо в выбранной EVM-сети, пересматривается
блокчейн-адаптер, а не требование архитектуры. Формат подписываемых байтов записи
также необходимо зафиксировать отдельно от транспортной сериализации.

## Состояние подключения

Выбор отражён в комментариях и шаблонах импортов. Новые библиотеки пока не добавлены
в `go.mod`: активного кода, использующего их, ещё нет. Версии нужно зафиксировать при
реализации соответствующего компонента и проверить на заявленной версии Go.
`transport.NewHost(ctx, cfg)` уже создаёт узел с настраиваемыми адресами,
необязательным relay, тайм-аутом подключения и освобождением ресурсов при ошибке.
Send-функции используют общий идентификатор протокола; маршрутизация через relay,
резервирование входящих соединений и приём сообщений ещё не реализованы.
`relay.GetPrivateKey(path)` уже реализует
загрузку существующего ключа или генерацию и сохранение нового при отсутствии файла.
